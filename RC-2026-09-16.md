# Known limitations

Read this section before onboarding anyone.

## 1. A registry change could publish a false "resolved" — FIXED, was the reason this RC moved

Kept here because it is the most instructive failure this project has had, and because anyone
auditing the RC should see it was found and closed rather than never noticed.

A finding exists only where a scanned occurrence **joins** a registry entry. The audit workflow
sets `MENDR_REGISTRY_REFRESH: 'on'` and fetches the **rolling** snapshot, so registry data moves
between runs while pinned code does not — by design (`freshRegistry.ts`: "pin the CODE, refresh
the DATA"). An entry that was re-keyed, re-statused or dropped therefore made a finding vanish
with **every surface healthy**. The existing guard only asked whether a surface *errored*; nothing
errored. The finding was reported **resolved**, `mayClose` returned true, the issue **closed**,
and the baseline was **erased** over a live exposure. Reproduced end to end through the real
rendering path during adversarial review.

**The fix.** Resolution identity is now `(scanner version, registry content hash)`, both recorded
in the baseline. A disappearance across a change to *either* is **held open**, not resolved. A
move is still reported, because it claims the finding still exists — the safe direction. An
unknown value on either side self-heals in one run rather than carrying forever.

**Honest limit that remains:** the scanner half is a package version, so a classifier change
*within* one release is invisible to it. The registry half is a content hash and is exact.

## 2. Tier A almost never fires on real code

Measured across the 12-repo validation corpus plus 14 outreach repositories: **one** Tier A
finding in 26 real repositories. Tier A requires the SDK client to resolve in the same file, and
production code injects or wraps its client. Expect a **report**, not a patch. Any pitch built on
"it opens the PR for you" will not survive contact with a real repository.

## 3. The verification environment is not isolated

It is a **secret-sanitized verification environment**: a throwaway copy with the CI's own
credentials stripped and captured output redacted at source. There is **no** network isolation, no
process or filesystem isolation, and no resource limits. Running a gate executes the repository's
own code with its own privileges. Full statement in `TRUST.md` §4b.

## 4. Behaviour is never verified

The gates prove a change builds and the existing tests pass. They prove nothing about whether the
replacement model matches the old one on quality, latency, cost or response shape. Every PR body
says so.

## 5. The recall measurement has a known blind spot

The 12-repo recall search narrowed occurrences to candidates using the scanner's own notion of a
candidate. It can catch an id sorted into the wrong bucket; it structurally **cannot** catch a
whole position the classifier misreads. That class was found by reading a repository by hand
(`going-doer/Paper2Code`), which produced v0.5.1-alpha.

## 6. Distribution is by git spec, not npm

`npx --yes "github:ajitheee/mendr#<sha>"`. The npm package name is unclaimed; `npx mendr` does
not work.

## 7. The approval loop has run on v0.5.7-alpha, not on this build

`mendr-demo` has four merged Mendr PRs: two from 2026-09-10, one from 2026-09-17, and #5 from
2026-09-28. A dispatched migrate run on v0.5.7-alpha's action opened #5 end to end, from claiming
the approval to reporting back to the App (§10).

The Approve-to-PR path has **not** been run on v0.5.8-alpha. `mendr-action/` is unchanged apart
from its version pins, but the CLI it runs is not: v0.5.8-alpha sends a swap that starts applying
a parameter rule to review instead of patching it.

## 8. Inherited uncertainty

Config selection other than an env-var read is not traced to a runtime reader ("reader tie-back
not proven"). Runtime usage is unmeasured unless telemetry is connected, so "is this live in
production" is unanswered by default.

## How the customer pins this

```yaml
uses: ajitheee/mendr/.github/workflows/reusable-audit.yml@701225323ca70e0ef13826fa63f50bae486e6339
uses: ajitheee/mendr/.github/workflows/reusable-migrate.yml@701225323ca70e0ef13826fa63f50bae486e6339
```

Set the repository variable `MENDR_SPEC` to the same SHA so the CLI it fetches is pinned too.

## 9. The migrate path is governed by a tag, not by your SHA

The audit path honours your pin completely: the workflow at your SHA, and the CLI via
`MENDR_SPEC`. The migrate path does not, and cannot be made to.

GitHub forbids an expression in a workflow's `uses:`, so `reusable-migrate.yml` must
name the Mendr action with a literal ref. Pinning that workflow to a commit SHA gets
you the file as it was at that SHA — and that file names **a tag**.

This was briefly "fixed" by making the CLI spec caller-overridable, which was worse: the
action is a thin wrapper that shells out to the CLI, so pinning the CLI while leaving the
wrapper on a tag decouples two things that must move together. A test in the App suite
(`app/src/ui/workflowTemplate.test.ts`) exists precisely to enforce that pair, and it
caught the attempt. The pair is intact; the tag dependency is real.

**The proper fix, not done under the freeze:** rewrite both refs to the release's own
commit SHA at release time, which needs a two-step release (commit, then rewrite the refs
to that commit and tag the result). The existing test already accepts a 40-character ref,
so nothing blocks it but the release process.

**Until then:** the migrate path's integrity rests on released tags never being moved.
Protect tags in repository settings, and treat a moved release tag as a security event.

## 11. Mendr failed on its own output file — FIXED 2026-09-17

Worth recording because of how it hid. The audit workflow ran
`mendr audit . --json > mendr-audit.json` from the repository root, and the shell creates that
file **before mendr starts**. So every run scanned mendr's own zero-byte output, the config
scanner called it malformed JSON, and the fail-closed rule turned the run `inconclusive`.

A run WITH findings concludes `exposure_detected` regardless of parse failures. So the bug could
only ever strike a repository that was **clean** — turning every all-clear into `inconclusive`
with a neutral check.

It surfaced the moment the demo completed its own loop: the migration PR was merged, the repo
became clean, and from that commit on every audit went red. The pull request mendr opened failed
the check mendr opened it with.

Fixed on both sides: an empty file is no longer treated as malformed configuration (it has no
content to misread, so its unreadability narrows nothing), and the report is now written to
`$RUNNER_TEMP`, outside the scanned tree. Verified on the demo: `success`, "no exposure in
completed surfaces".
